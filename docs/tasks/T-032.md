# T-032 — Fecha y hora en operaciones de inversión (Room v6)

- **Estado:** pendiente
- **Rama:** `codex/t-032-hora-operaciones`
- **Rama base:** `claude/fase-3-mvp` (tras integrar T-031)
- **Depende de:** T-029, T-030 (aceptadas)
- **Riesgo:** medio-alto (modelo Room y migración 5→6, orden de `PositionCalculator` que afecta el coste medio ponderado)
- **Tipo:** implementación

## Objetivo
Backlog del usuario tras probar T-029 (B1): «las operaciones de inversión deben poder llevar fecha **y hora/minuto**, no solo el día», porque varias operaciones del mismo día en distinto orden real afectan a qué precio de compra se usa al calcular ventas parciales (coste medio ponderado) y en qué orden se muestran.

## Contexto y contratos
- `InvestmentOperationEntity` (Room, `data/db/Entities.kt`): campo `epochDay: Long` (solo día). Dominio `InvestmentOperation.date: LocalDate` (`domain/model/Models.kt`). Mapper en `data/db/Mappers.kt` (`toDomain`/`toEntity`).
- Orden actual: `PositionCalculator.compute` ordena `operations.sortedWith(compareBy({ it.date }, { it.createdAt }))` — usa `createdAt` (instante de inserción en la app) como desempate, NO la hora real de la operación. Esto es lo que hay que sustituir por una hora real editable por el usuario.
- Se construyen operaciones en `ui/investments/InvestmentsViewModel.kt` (`addOperation`) y se leen en `ui/investments/AssetDetailViewModel.kt` (historial del activo).
- Diálogo de creación: `ui/investments/InvestmentDialogs.kt` (`OperationDialog`), ya tiene selector de fecha; añade selector de hora.

## Decisiones ya cerradas e invariantes
1. **Room v6, migración 5→6 SIN pérdida de datos y aditiva:** añade a `investment_operation` la columna `secondOfDay INTEGER NOT NULL DEFAULT 0` (segundos desde medianoche, 0–86399; el valor 0 = 00:00 para todas las operaciones existentes, que no tenían hora). NO se toca `epochDay` (se mantiene tal cual para no romper el resto del código que ya usa `date: LocalDate`). Sin `fallbackToDestructiveMigration`; test de migración con una base v5 real (mismo patrón que `Migration4to5Test.kt`: `FrameworkSQLiteOpenHelperFactory`, no Room en memoria desde cero) con operaciones existentes, comprobando que `secondOfDay` queda a 0 y el resto de columnas se conserva. Exporta `app/schemas/**/6.json` (`exportSchema = true`).
2. **Dominio:** `InvestmentOperation` gana `val time: LocalTime = LocalTime.MIDNIGHT` (nuevo parámetro con valor por defecto al final de la data class, para no romper otras llamadas posicionales existentes que no lo pasen). Mapper: `toDomain()` construye `time = LocalTime.ofSecondOfDay(secondOfDay.toLong())`; `toEntity()` guarda `secondOfDay = time.toSecondOfDay()`.
3. **Orden:** `PositionCalculator.compute` (y cualquier otro sitio que ordene operaciones de un mismo activo/cartera para calcular coste medio ponderado o rentabilidad) pasa a ordenar por `compareBy({ it.date }, { it.time }, { it.createdAt })` — `time` decide el orden dentro del mismo día; `createdAt` sigue como desempate final si coincide fecha+hora exacta. Revisa también el historial mostrado en `AssetDetailScreen`/`AssetDetailViewModel` (debe listarse en el mismo orden cronológico real, no por `createdAt`).
4. **UI del diálogo de operación (`OperationDialog`, `InvestmentDialogs.kt`):** añade un selector de hora (`TimePicker`/`TimePickerDialog` de Material 3, o un campo de texto HH:mm si el proyecto no usa ya `TimePicker` en ningún sitio — comprueba antes de añadir un componente nuevo) junto al selector de fecha existente. **Para una operación NUEVA, el valor por defecto es la hora actual** (`LocalTime.now()`), no medianoche (así las operaciones nuevas quedan bien ordenadas entre sí sin que el usuario tenga que recordar poner la hora). Al editar una operación existente sin hora registrada (importada o de antes de esta ficha), se muestra 00:00 y el usuario puede corregirla. Validación: hora obligatoria en el sentido de que siempre hay un valor (no puede quedar vacía), sin rango restringido (cualquier hora del día es válida).
5. **Compatibilidad con T-018/T-019/T-023 (aportaciones a cartera vía transferencia y notificaciones):** las transferencias (`Transfer`) y transacciones (`Transaction`) NO llevan hora en esta ficha (siguen siendo `epochDay`/`LocalDate`); esto es solo para `InvestmentOperationEntity`. No amplíes el alcance a otras tablas.
6. **General:** nada de `Double`/`Float`; sigue con `BigDecimal`/enteros para dinero y cantidades. Cumple `docs/tasks/COMMON.md` (tests de ViewModel con `setMain`+`runTest`+`uiState.first{}`; pantallas con cabecera propia usan `hasOwnTopBar`+`statusBarsPadding()`; revisa con cuidado imports y llamadas con lambda final, porque no puedes compilar — en las dos últimas fichas los únicos fallos de compilación reales vinieron de eso).

# T-039 — Tests intermitentes de ViewModel en la suite completa (causa raíz + aislamiento)

- **Estado:** pendiente
- **Rama:** `codex/t-039`
- **Rama base:** `claude/fase-3-mvp` (tras integrar T-038)
- **Depende de:** ninguna funcional
- **Riesgo:** bajo-medio (solo infraestructura de tests; prohibido cambiar comportamiento de producción salvo lo indicado)
- **Tipo:** investigación + corrección

## Objetivo
Encontrar y eliminar la causa raíz de los fallos intermitentes de tests Robolectric de ViewModel que solo aparecen al ejecutar la suite completa (`gradlew testDebugUnitTest`) y nunca al ejecutar la clase aislada. Van 4 apariciones (`InvestmentsViewModelTest` ×3, `MovementsViewModelTest` ×1), cada vez en un test distinto.

## Síntomas registrados
- `kotlinx.coroutines.test.UncompletedCoroutinesError: After waiting for 1m, the test body did not run to completion` (el `uiState.first { ... }` nunca se cumple).
- `java.io.IOException` suelto en `FileStorage.kt:114` (DataStore) con el XML del test marcado como correcto.
- Al final de la suite aparecen en stderr trazas de `androidx.room.TransactionExecutor` / `SQLiteOpenHelper.getWritableDatabase` desde `RoomDatabase.withTransaction`: transacciones lanzadas desde `viewModelScope` que siguen vivas cuando el test ya ha hecho `db.close()`.
- Aislado (`--tests "*MovementsViewModelTest*"`) pasa 3/3.

## Hipótesis a verificar (no las des por buenas sin evidencia)
1. **DataStore compartido:** `SettingsRepository` usa `preferencesDataStore(name = "settings")`, un único fichero para todo el JVM de tests. El estado se filtra entre tests y clases, y las escrituras de una clase pueden solaparse con otra. Ya se ha visto una fuga real de `movements_all_accounts` entre tests (T-037).
2. **Corrutinas huérfanas:** los ViewModels no se limpian (`viewModelScope` no se cancela) al final de cada test, así que sus `launch` siguen escribiendo en Room/DataStore después de `db.close()` y contaminan tests posteriores.
4. **(Hipótesis principal de Claude, 2026-09-28) DataStore ligado a un directorio borrado.** `private val Context.settingsStore by preferencesDataStore(name = "settings")` crea un singleton que se ata al `applicationContext` del PRIMER test que lo usa. Robolectric reutiliza el classloader entre tests pero crea y borra un directorio de datos distinto por test, así que los tests posteriores escriben contra una ruta ya borrada → `IOException` en `FileStorage.kt:114` (visto en la suite). Los ViewModels capturan ese error con `runCatching` (`errors.value = ...`), el estado esperado nunca llega y `uiState.first { ... }` agota los 60 s. Encaja con: solo falla en suite completa, siempre en clases de ViewModel que escriben ajustes, cada vez en una distinta según el orden. Evidencia reciente: los 3 tests de `MovementAccountsViewModelTest` agotan el tiempo en la suite completa (T-037 y T-038) y pasan aislados. Verifícalo (p. ej. comprobando la ruta del fichero del DataStore entre dos tests) antes de corregir.
3. **Carga:** la máquina tiene ~3,5 GB de RAM libre; el timeout de 60 s de `runTest` puede agotarse bajo presión, pero eso solo explicaría la lentitud, no una condición que nunca se cumple.

## Decisiones ya cerradas
- Se permite un cambio mínimo en producción para poder inyectar el almacenamiento de ajustes en tests (por ejemplo, un constructor secundario de `SettingsRepository` que reciba un `DataStore<Preferences>`, o un parámetro con valor por defecto). El comportamiento en la app real debe quedar idéntico (mismo fichero `settings`, mismas claves y valores por defecto).
- Cada test que use ajustes debe tener un DataStore propio y aislado (p. ej. `PreferenceDataStoreFactory.create` con un fichero en `TemporaryFolder` y un `scope` propio que se cancele en `@After`).
- Los ViewModels creados en tests deben limpiarse en `@After` (p. ej. `ViewModelStore().clear()` o equivalente) **antes** de `db.close()`.
- Si comunes a varios tests, extrae un helper de test (`app/src/test/.../testutil/`) en vez de duplicar código.
- No subas el timeout de `runTest` como «solución»; solo es aceptable como medida adicional si demuestras que la causa raíz está corregida.

## Objetivo
`datos-privados/Documento de cambios/Documento.md`, sección «Más» (referencia visual `figuras/figura4.jpg`, app Mi Presupuesto): gestionar «órdenes permanentes», que son apuntes (gasto/ingreso/transferencia) que se repiten periódicamente. El formulario es el mismo que ya existe para un apunte normal, ampliado con:
1. **Periodo (cantidad):** número entero, cada cuántas unidades se repite.
2. **Periodo (tipo):** días, meses o años.
3. **Fecha de expiración (check):** si está marcado, habilita un campo de fecha de fin; si no, la orden no tiene fin.
4. **Fecha de expiración (fecha):** última fecha en la que la orden genera movimientos.
5. **Recordatorio:** selector (No / Exacto / 1 día antes / 2 días antes / … / Personalizado). Si es distinto de «No», se envía una notificación push recordando el movimiento.

**Importante — no está en el texto del usuario, no lo añadas:** la captura de referencia (`figura4.jpg`) muestra también «Utilizar plantilla», «Si la fecha cae en fin de semana» y «Agregar foto». El usuario solo pidió los 5 campos de arriba; no repliques el resto de la captura, es solo referencia visual del estilo del formulario.

## Contexto y contratos
- `domain/model/Models.kt`: `Transaction` ya tiene `source: TransactionSource` con el valor `RECURRENTE` **ya reservado en el enum mismo** (`enum class TransactionSource { MANUAL, IMPORTACION, NOTIFICACION, RECURRENTE }`), pensado exactamente para esto — no lo cambies de nombre.
- `ui/movements/EntryFormScreen.kt`/`EntryFormViewModel.kt`: formulario unificado de apunte (gasto/ingreso/transferencia) ya existente, con selector de categoría, cuenta, importe, fecha (T-025/T-026). Esta ficha añade una **variante extendida** de ese formulario para crear/editar una orden permanente, reutilizando sus componentes en vez de duplicar el formulario entero.
- No existe hoy: ninguna entidad Room de recurrencia, ningún uso de `WorkManager` (la dependencia `androidx.work:work-runtime-ktx` YA está declarada en `app/build.gradle.kts` y en `gradle/libs.versions.toml`, pero no se usa en ningún sitio — no necesitas tocar Gradle), ninguna notificación local propia de la app (el único uso de notificaciones hoy es `notifications/NotificationAccess.kt`, que es para LEER notificaciones bancarias, no para publicar las propias; no lo toques).
- Precedente de decisión de producto (ver `PROJECT_MEMORY.md` sección 26, D-009 y siguientes, y el criterio ya aplicado a notificaciones bancarias): el usuario prefiere que los movimientos se **creen directamente** y se corrijan después, en vez de un sistema de propuestas pendientes. Aplica el mismo criterio aquí: una orden permanente **genera transacciones reales** (`Transaction` con `source = RECURRENTE`) en sus fechas correspondientes, no una cola de confirmación pendiente aparte. El usuario podrá editarlas o borrarlas como cualquier apunte normal después.
- Los movimientos se generan **cuando llega su fecha** (hasta hoy inclusive), nunca por adelantado: ver «Revisión de Claude — ronda 2».

## Decisiones ya cerradas e invariantes
### Room v8, migración 7→8 (nueva tabla)
1. Nueva entidad `RecurringRuleEntity` (tabla `recurring_rule`): `id TEXT PK`, `kind TEXT` (GASTO/INGRESO/TRANSFERENCIA), `amountMinor INTEGER`, `currency TEXT`, `accountId TEXT` (FK → `account.id`, `ON DELETE RESTRICT`, la cuenta de origen/única para gasto-ingreso), `destinationAccountId TEXT?` (FK opcional, solo si `kind = TRANSFERENCIA`), `categoryId TEXT?` (FK opcional → `category.id`, `ON DELETE SET NULL`), `description TEXT`, `merchant TEXT`, `startEpochDay INTEGER` (primera ejecución/fecha de inicio), `periodQuantity INTEGER` (entero > 0), `periodUnit TEXT` (DIA/MES/ANIO), `endEpochDay INTEGER?` (NULL = sin fin), `reminder TEXT` (NO/EXACTO/UN_DIA_ANTES/DOS_DIAS_ANTES/PERSONALIZADO), `reminderCustomDays INTEGER?` (solo si `reminder = PERSONALIZADO`), `lastGeneratedEpochDay INTEGER?` (última fecha ya generada, para no duplicar), `archived BOOLEAN NOT NULL DEFAULT 0`, `createdAt INTEGER`, `updatedAt INTEGER`. Índices por `accountId`, `categoryId`. Exporta `8.json`, sin `fallbackToDestructiveMigration`, con su test de migración (aunque sea una tabla nueva sin datos previos que migrar, sigue el mismo patrón de test que las migraciones anteriores).
2. Dominio: `RecurringRule` + enums `RecurringPeriodUnit { DIA, MES, ANIO }` y `ReminderOption { NO, EXACTO, UN_DIA_ANTES, DOS_DIAS_ANTES, PERSONALIZADO }`. Repositorio (nuevo o dentro de `LedgerRepository`) con CRUD + listado activo/archivado.

### Motor de generación (control reforzado, dominio puro + WorkManager)
3. Función pura, por ejemplo `domain/calc/RecurringGenerator.kt`: dado una `RecurringRule` y una fecha límite (normalmente hoy, o hoy + un margen razonable para poder ver los próximos movimientos futuros en gris, p. ej. hoy + 1 mes — decide un margen razonable y documéntalo), calcula qué fechas de ejecución faltan por generar desde `lastGeneratedEpochDay` (o `startEpochDay` si nunca se generó nada) hasta el límite, respetando `periodQuantity`/`periodUnit` y `endEpochDay`. Devuelve la lista de fechas a generar; no accede a la base de datos (función pura, testeable).
4. Aplicación del resultado: por cada fecha pendiente, crea una `Transaction` (o `Transfer` si `kind = TRANSFERENCIA`) real con `source = RECURRENTE`, los datos de la regla, y actualiza `lastGeneratedEpochDay`. Debe ser idempotente: ejecutar el proceso dos veces seguidas no debe duplicar movimientos (test obligatorio, mismo tipo de caso límite que ya exige el proyecto para notificaciones/importaciones: «una generación duplicada no crea dos apuntes»).
5. Ejecuta este proceso: (a) al abrir la app (comprobación puntual, p. ej. desde donde ya se inicializa el contenedor de dependencias), y (b) periódicamente en segundo plano con `WorkManager` (`PeriodicWorkRequest`, una vez al día es suficiente; ten en cuenta las restricciones de Android de que un `PeriodicWorkRequest` tiene un intervalo mínimo de 15 minutos y que el sistema puede retrasarlo — no asumas ejecución exacta a una hora concreta). Registra el `Worker` en `AppContainer`/`MiPatrimonioApplication` siguiendo el patrón de inicialización ya usado en el proyecto para otros servicios.

### Notificaciones locales de recordatorio (nuevas)
6. Añade el permiso `POST_NOTIFICATIONS` al manifiesto (Android 13+, se solicita en tiempo de ejecución) y un `NotificationChannel` propio de recordatorios de órdenes permanentes (nombre e importancia en español, coherente con lo que ya pide CLAUDE.md §24 sobre notificaciones locales: presupuestos, recurrentes, propuestas, objetivos).
7. Si `reminder != NO`, programa (con `WorkManager`, `OneTimeWorkRequest` con el delay calculado, o recalculado dentro del mismo worker periódico) una notificación local el día correspondiente (mismo día de la ejecución si es «Exacto», 1/2 días antes, o los días que indique «Personalizado») recordando el movimiento antes de que se genere o el mismo día. Si el usuario no concede el permiso de notificaciones, la orden permanente debe seguir funcionando igual (se generan los movimientos igualmente, simplemente no hay recordatorio) — nunca bloquees la función principal por falta de este permiso opcional.

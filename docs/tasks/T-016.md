## Objetivo

Construir la lógica de la FASE 6 (CLAUDE.md §13) que decide, a partir del texto de una notificación bancaria, si debe convertirse en una propuesta de movimiento pendiente de confirmación. Todo en esta ficha es **lógica pura + persistencia**, verificable con tests JVM. **No incluye** `NotificationListenerService`, permisos de Android ni ninguna pantalla: eso será una ficha posterior (T-017) que dependerá de esta.

Al terminar debe existir: un modelo de notificación reducida, un motor de reglas con adaptadores intercambiables por banco, un intérprete genérico en español, persistencia Room de las reglas de autorización y de las propuestas pendientes, y un repositorio que las conecta todo con deduplicación.

## Decisiones ya cerradas e invariantes (no las reabras)

1. **Nunca se crea un movimiento real automáticamente.** El resultado de esta tarea es como mucho una fila en una tabla de propuestas pendientes; convertirla en `Transaction`/`Transfer` es una acción explícita del usuario que hará T-017 sobre el repositorio ya existente (`LedgerRepository`), no esta ficha.
2. **Privacidad**: no se persiste el texto completo de la notificación ni el nombre de la app tal cual la ve el usuario más allá del `packageName`. No se guardan campos que parezcan códigos de un solo uso, contraseñas o claves.
3. **Dinero**: los importes de las propuestas se guardan en unidades menores (`Long`), igual que en el resto del dominio (`domain/model/Money.kt`, que no debes modificar). Nunca `Double`/`Float`.
4. **No declares compatibilidad con ningún banco concreto.** El motor debe funcionar con un intérprete genérico en español y una interfaz para que en el futuro se añadan adaptadores específicos sin tocar el motor. No inventes patrones de bancos reales que no hayas verificado: implementa solo el intérprete genérico descrito abajo.
5. Migración Room: la base de datos está en versión 1 (`app/src/main/java/com/mipatrimonio/app/data/db/AppDatabase.kt`, `exportSchema = true`, esquema en `app/schemas/`). Esta ficha la sube a **versión 2** añadiendo tablas nuevas exclusivamente (no se toca ninguna tabla ni columna existente). Debes escribir una `Migration(1, 2)` explícita con `CREATE TABLE`; **prohibido `fallbackToDestructiveMigration`**.

## Requisitos detallados

### 1. Modelos (`NotificationModels.kt`)

```kotlin
data class BankNotification(val packageName: String, val title: String, val text: String, val postedAt: Long)

enum class ProposalKind { GASTO, INGRESO, TRANSFERENCIA }
enum class Confidence { ALTA, MEDIA, BAJA }

data class ParsedNotification(
    val kind: ProposalKind, val amountMinor: Long, val currency: String,
    val merchant: String?, val confidence: Confidence, val parserId: String,
)
```

`amountMinor` siempre positivo (el signo lo decide `kind`, no el importe).

### 2. Interfaz de adaptador y motor genérico

```kotlin
interface BankNotificationParser {
    val parserId: String
    fun accepts(packageName: String): Boolean
    fun parse(notification: BankNotification): ParsedNotification?
}
```

`GenericSpanishParser` implementa esta interfaz, `accepts` devuelve siempre `true` (es el parser por defecto cuando ningún adaptador específico reclama el paquete). Debe:

- **Descartar por completo** (devolver `null`) cualquier notificación cuyo texto (insensible a mayúsculas) contenga alguna de estas señales de contenido sensible: `codigo`, `código`, `clave`, `contraseña`/`contrasena`, `otp`, `pin`, `verificación`/`verificacion`, `token`. Esto tiene prioridad sobre cualquier otra interpretación.
- Reconocer un importe únicamente si va acompañado de una marca de divisa reconocible (símbolo `€`/`$`/`£` o palabra `eur`/`euros`/`usd`/`dólares`/`gbp`/`libras`, sin distinguir mayúsculas). Un número sin marca de divisa **no** se interpreta como importe (evita confundir un número de operación con un importe). Interpreta el número con `MoneyMath.parse` salvo el caso "un separador seguido de exactamente 3 cifras", que son millares, no decimales (p. ej. `"1.234"` = mil doscientos treinta y cuatro, no 1,234).
- Clasificar en `GASTO`, `INGRESO` o `TRANSFERENCIA` buscando palabras clave en español (por ejemplo: gasto → "compra", "pago", "cargo", "recibo", "domiciliaci..."; ingreso → "ingreso", "abono", "nómina", "devolución"; transferencia → "transferencia", "bizum", "traspaso"). Si no reconoce ninguna palabra clave, devuelve `null` (no propone nada) en vez de adivinar.
- Extraer el comercio cuando el texto contenga el patrón `"en <algo>"`, descartando resultados que empiecen por expresiones genéricas como "tu cuenta", "su cuenta", "tu tarjeta".
- Asignar `confidence`: `BAJA` para transferencias (no se puede saber si es entre cuentas propias sin preguntar), `ALTA` si hay comercio identificado, `MEDIA` en el resto.

### 3. Motor (`NotificationEngine.kt`)

```kotlin
sealed interface NotificationOutcome {
    data object AppNoAutorizada : NotificationOutcome
    data object NoInterpretable : NotificationOutcome
    data class Duplicada(val existenteId: String) : NotificationOutcome
    data class Nueva(val propuesta: PendingProposalDraft) : NotificationOutcome
}

class NotificationEngine(private val parsers: List<BankNotificationParser>) {
    fun process(
        notification: BankNotification,
        authorizedPackages: Set<String>,
        accountIdFor: (String) -> String?,
        recentProposals: List<PendingProposalDraft>,
    ): NotificationOutcome
}
```

(Ajusta el nombre exacto `PendingProposalDraft` si te encaja mejor como el modelo de propuesta antes de tener id de base de datos; documenta la firma final en tu informe si difiere.)

Reglas:

1. Si `notification.packageName` no está en `authorizedPackages` → `AppNoAutorizada`, **sin interpretar el texto**.
2. Si está autorizada: probar los `parsers` en orden, usando el primero cuyo `accepts(packageName)` sea `true`; si ninguno interpreta nada (todos devuelven `null`) → `NoInterpretable`. `GenericSpanishParser` debe estar siempre en la lista (normalmente el último, como respaldo).
3. Deduplicación: calcula una huella a partir de `packageName + kind + amountMinor + currency + merchant` (normalizando el comercio a minúsculas y sin espacios en los extremos). Si `recentProposals` ya contiene una con la misma huella **y** un `postedAt` dentro de una ventana de 5 minutos respecto a la notificación actual, devuelve `Duplicada` con el id de esa propuesta existente. Si no, `Nueva`.
4. `accountIdFor(packageName)` da la cuenta asociada a esa app (puede ser `null` si el usuario todavía no la ha vinculado); guárdalo en la propuesta aunque sea `null`.

### 4. Persistencia (entidades, migración, repositorio)

Dos tablas nuevas:

- **Regla de autorización** por paquete: id (usa el propio `packageName` como clave primaria), si está activa, la cuenta asociada (nullable, sin `ForeignKey` estricta porque el usuario puede desvincular una cuenta más tarde — documenta esta decisión en el informe si la tomas), `createdAt`.
- **Propuesta pendiente**: id (`String`, `UUID`), `packageName`, `accountId` (nullable), `kind` (texto), `amountMinor` (`Long`), `currency`, `merchant` (nullable), `confidence` (texto), `parserId`, `postedAt` (`Long`), `status` (por ejemplo `PENDIENTE`/`CONFIRMADA`/`DESCARTADA`, como texto), `resultingTransactionId` (nullable, se rellena cuando T-017 la confirme), `createdAt`.

`NotificationRepository` expone (nombres orientativos, ajústalos a lo que ya haga el resto del proyecto):

- `Flow` de reglas de autorización y `Flow` de propuestas pendientes (`status == PENDIENTE`).
- `suspend fun setAuthorized(packageName: String, authorized: Boolean, accountId: String?)`.
- `suspend fun ingest(notification: BankNotification): NotificationOutcome` — junta el motor (`NotificationEngine`) con el estado persistido: lee reglas activas y propuestas recientes, llama a `process`, y si el resultado es `Nueva` la guarda con `status = PENDIENTE` y devuelve el resultado con el id ya asignado.
- Funciones para que T-017 pueda marcar una propuesta como confirmada o descartada (sin crear todavía el movimiento real: eso es responsabilidad de T-017, que llamará a `LedgerRepository`).

## Casos límite a cubrir

- Notificación de una app no autorizada (con y sin importe válido en el texto).
- Notificación que contiene una palabra sensible junto a un importe: debe descartarse igualmente.
- Importe sin marca de divisa: no se interpreta.
- Dos notificaciones idénticas en menos de 5 minutos → la segunda es `Duplicada`; con más de 5 minutos de diferencia → ambas son `Nueva`.
- Mismo importe y comercio pero `kind` distinto (p. ej. un gasto y una devolución del mismo importe) → no son duplicadas entre sí.
- Texto sin ninguna palabra clave reconocible → `NoInterpretable`.
- Importe con formato de millares (`"1.234,50 €"`) y con decimales simples (`"12,50 €"`).
- `accountIdFor` devuelve `null` (app autorizada pero sin cuenta vinculada todavía): la propuesta se guarda igualmente con `accountId = null`.
- Migración 1→2 aplicada sobre una base de datos v1 con datos ya existentes (cuentas, movimientos): deben conservarse intactos.

# T-015 — Parser CSV genérico + adaptador de Trade Republic

- **Estado:** en curso
- **Rama:** `codex/t-015-csv-parser`
- **Depende de:** nada (lógica pura, aislada del resto de la app)

## Objetivo

Crear la base de la importación de movimientos desde CSV: un parser genérico correcto y un adaptador que traduzca el export de Trade Republic a un modelo intermedio revisable por el usuario.

Al terminar debe existir lógica pura, sin UI y sin base de datos, capaz de convertir el texto de un CSV en una `ImportPreview` con movimientos normalizados, duplicados detectados e incidencias. La escritura en Room y la pantalla de importación NO son parte de esta tarea: las hará Claude después consumiendo estos tipos.

## Contexto y contratos

`domain/model/Money.kt` ya existe y **los importes se representan en céntimos como `Long`** (2 decimales, redondeo `HALF_EVEN`). Las cantidades de activos y los precios usan `BigDecimal` porque traen muchos decimales.

En esta tarea **no puedes importar ni modificar nada de `domain/`**. Define lo que necesites dentro de tu propio paquete. Para convertir texto a céntimos escribe tu propia función privada en `data/importer/` con `BigDecimal` y `setScale(2, RoundingMode.HALF_EVEN)`; **nunca uses `Double` ni `Float` para dinero**, ni siquiera de paso.

### Formato real del export de Trade Republic

Cabecera exacta, en este orden:

```
datetime,date,account_type,category,type,asset_class,name,symbol,shares,price,amount,fee,tax,currency,original_amount,original_currency,fx_rate,description,transaction_id,counterparty_name,counterparty_iban,payment_reference,mcc_code
```

Características verificadas sobre un export real de 465 filas:

- UTF-8, todos los campos entre comillas dobles, separador coma, **punto** como separador decimal.
- `date` en formato ISO `YYYY-MM-DD`; `datetime` ISO en UTC.
- `transaction_id` es **único** en el fichero: es la clave natural de deduplicación.
- `amount` viene **con signo**: negativo significa salida de dinero.
- `fee` y `tax` van en columnas propias y casi siempre vacías.
- Algunas filas traen `original_amount` + `original_currency` (p. ej. USD) y `fx_rate`.
- Algunas filas tienen `currency` vacía.
- Los activos se identifican por **ISIN en la columna `symbol`**, no por ticker.
- `shares` y `price` traen muchos decimales.
- `CARD_TRANSACTION` no trae `counterparty_name`: el comercio hay que sacarlo de `description`. Suele traer `mcc_code`.

Valores observados en `category`: `CASH`, `TRADING`, `CORPORATE_ACTION`, `DELIVERY`.

Valores observados en `type`: `CARD_TRANSACTION`, `CARD_TRANSACTION_INTERNATIONAL`, `TRANSFER_INSTANT_INBOUND`, `TRANSFER_INSTANT_OUTBOUND`, `TRANSFER_DIRECT_DEBIT_INBOUND`, `TRANSFER_INBOUND`, `INTEREST_PAYMENT`, `DIVIDEND`, `BUY`, `SELL`, `PRIVATE_MARKET_BUY`, `BENEFITS_SAVEBACK`, `LIQUIDATION_PROCEEDS`, `IPO_SUBSCRIPTION`, `INTERMEDIATE_SECURITIES_DISTRIBUTION`, `LIQUIDATION_DIVIDEND`, `FREE_DELIVERY`, `BONUS`, `FEE`, y variantes con sufijo `_CANCELLED`.

### Trampa de doble contabilización (importante)

Las filas `type=BUY` con `asset_class=PRIVATE_FUND` llegan **con `amount` vacío**. Su salida de caja real está en una fila aparte con `type=PRIVATE_MARKET_BUY` e importe negativo.

Si cuentas las dos, el gasto se duplica. Regla: la fila `BUY`/`PRIVATE_FUND` sin importe **no genera movimiento de caja** (`amountCents = 0`) y se marca `needsReview = true` con motivo; la fila `PRIVATE_MARKET_BUY` sí lleva el importe.

## Requisitos detallados

### 1. `CsvParser` — parser genérico correcto

```kotlin
data class CsvTable(val headers: List<String>, val rows: List<CsvRow>)

data class CsvRow(val lineNumber: Int, val values: Map<String, String>) {
    operator fun get(column: String): String
}

object CsvParser {
    fun parse(text: String, separator: Char = ','): CsvTable
}
```

Debe cumplir RFC 4180 en lo esencial:

1. Campos entre comillas dobles; dentro pueden aparecer el separador, saltos de línea y comillas escapadas duplicándolas (`""`).
2. Campos sin comillas también válidos; se recortan los espacios de los extremos (los que van dentro de comillas se respetan tal cual).
3. Acepta saltos `\n` y `\r\n`.
4. Ignora un BOM UTF-8 inicial si está presente.
5. Ignora líneas completamente vacías.
6. `lineNumber` es el número de línea física del fichero donde empieza la fila (la cabecera es la línea 1), útil para informar de errores.
7. `CsvRow.get` devuelve cadena vacía si la columna no existe, en vez de lanzar excepción.
8. Si una fila tiene **menos** campos que la cabecera, las columnas que faltan valen cadena vacía. Si tiene **más**, los sobrantes se descartan. En ambos casos no se lanza excepción: es el adaptador quien decide si eso es un problema.

### 2. Modelo intermedio

```kotlin
enum class ImportedKind { GASTO, INGRESO, COMPRA, VENTA, DIVIDENDO, INTERES, COMISION, IMPUESTO, TRANSFERENCIA, DESCONOCIDO }

data class ImportedMovement(
    val externalId: String,
    val date: LocalDate,
    val kind: ImportedKind,
    val amountCents: Long,
    val currency: String?,
    val description: String,
    val counterparty: String?,
    val isin: String?,
    val assetName: String?,
    val shares: BigDecimal?,
    val price: BigDecimal?,
    val feeCents: Long,
    val taxCents: Long,
    val originalAmountCents: Long?,
    val originalCurrency: String?,
    val fxRate: BigDecimal?,
    val mccCode: String?,
    val needsReview: Boolean,
    val reviewReason: String?,
    val rawType: String,
)

data class ImportIssue(val lineNumber: Int, val message: String)

data class ImportPreview(
    val movements: List<ImportedMovement>,
    val duplicateIdsInFile: List<String>,
    val issues: List<ImportIssue>,
)
```

`amountCents` conserva el signo del origen: negativo = salida de dinero.

Los mensajes de `ImportIssue.message` y de `reviewReason` van **en español** (son cadenas de diagnóstico que Claude mostrará después en la UI; no hace falta que estén en `strings.xml` en esta tarea, pero escríbelos en español y sin datos sensibles).

### 4. `TradeRepublicCsvAdapter`

- `id = "trade_republic"`, `displayName = "Trade Republic"`.
- `matches` devuelve true si están presentes al menos las columnas `transaction_id`, `date`, `amount` y `type`.
- Deduplicación: si un `transaction_id` aparece más de una vez, se conserva **la primera aparición** y las siguientes se añaden a `duplicateIdsInFile` (sin repetir el id en esa lista) y no generan movimiento.
- Clasificación en `ImportedKind` a partir de `type` y `category`:
  - `BUY`, `PRIVATE_MARKET_BUY`, `IPO_SUBSCRIPTION` → `COMPRA`
  - `SELL` → `VENTA`
  - `DIVIDEND`, `LIQUIDATION_DIVIDEND`, `INTERMEDIATE_SECURITIES_DISTRIBUTION` → `DIVIDENDO`
  - `INTEREST_PAYMENT` → `INTERES`
  - `FEE` → `COMISION`
  - `CARD_TRANSACTION`, `CARD_TRANSACTION_INTERNATIONAL` → `GASTO`
  - cualquier `TRANSFER_*` → `TRANSFERENCIA`
  - `BENEFITS_SAVEBACK`, `BONUS`, `LIQUIDATION_PROCEEDS` → `INGRESO`
  - `FREE_DELIVERY` y todo lo no reconocido → `DESCONOCIDO`
- Todo `type` terminado en `_CANCELLED` se clasifica por su tipo base pero con `needsReview = true` y motivo indicando que es una operación cancelada.
- `needsReview = true` además en estos casos, con su motivo:
  - cualquier `TRANSFERENCIA` (no se puede saber si es entre cuentas propias o con un tercero sin preguntar al usuario);
  - `DESCONOCIDO`;
  - `BUY` de `PRIVATE_FUND` sin importe (ver trampa de doble contabilización);
  - fila sin `currency`.
- `description`: usa `description` si no está vacía; si lo está, cae a `payment_reference`, luego a `name`, y si todo falta, a cadena vacía.
- `counterparty`: usa `counterparty_name`; si está vacía, `null`. **No** intentes adivinar el comercio troceando `description`: eso lo hará la UI con el usuario delante.
- `isin`: el contenido de `symbol` si no está vacío, `null` si lo está.
- `mccCode`: solo si no está vacío.
- Nunca incluyas `counterparty_iban` en el modelo de salida (dato sensible que esta capa no necesita).

### 5. Errores por fila

Una fila con un problema **no debe abortar la importación entera**. Se omite esa fila, se añade un `ImportIssue` con su `lineNumber` y el resto continúa. Motivos de omisión:

- `transaction_id` vacío;
- `date` ausente o no parseable como ISO;
- `amount` no vacío pero no parseable como número.

Un `amount` **vacío** no es un error: vale `0` céntimos (y activa `needsReview` en el caso del fondo privado).

## Casos límite a cubrir

- Fichero vacío, y fichero que solo tiene cabecera.
- Campo entrecomillado que contiene comas, comillas escapadas y un salto de línea.
- BOM UTF-8 al principio.
- Terminaciones de línea `\r\n`.
- Importes negativos, con y sin decimales, y con más de dos decimales (se redondea a céntimos con `HALF_EVEN`).
- `shares` y `price` con muchos decimales: no deben perder precisión.
- Fila sin divisa.
- Fila con `original_amount` / `original_currency` / `fx_rate`.
- `transaction_id` repetido.
- Fecha inválida.
- `type` desconocido.

## Tests obligatorios

En `CsvParserTest`, como mínimo: comillas con comas dentro, comillas escapadas, salto de línea dentro de un campo, BOM, `\r\n`, fichero vacío, solo cabecera, fila con menos y con más campos que la cabecera.

4. Una transferencia queda con `needsReview == true`.
5. Una fila con fecha inválida se omite y genera un `ImportIssue` con el `lineNumber` correcto, sin tirar el resto de la importación.
6. Una fila con `original_currency` USD conserva `originalAmountCents`, `originalCurrency` y `fxRate`.
7. Un importe con tres decimales se redondea correctamente a céntimos.
8. `matches` devuelve true con la cabecera real y false con una cabecera ajena.
